# ResourceTable performance audit — 8 000 Kubernetes resources

Статус: **аудит и предложения**; R1–R6 реализованы.

## 0. Статус реализации

- **R1 — реализовано.** `allSelected` мемоизирован и не перебирает 8 000 строк
  на каждом scroll-рендере.
- **R2 — реализовано.** `sorted` не инвалидируется изменениями Map, которые не
  участвуют в активной сортировке.
- **R3 — реализовано (частично).** Для watch-обновлений без изменения
  sort-значения сохраняется прежний порядок и заменяются только object
  references; добавления/удаления и изменения sort-значения по-прежнему делают
  полную сортировку.
- **R4 — реализовано.** `selectedObjects`/`selectedInView` мемоизированы и не
  сканируют список при пустом выборе.
- **R5 — реализовано.** `resourceStatus` кешируется по object reference в
  WeakMap; неизменённые строки не пересчитывают статус.
- **R6 — реализовано (первый шаг).** Ресайз колонки обновляет preview через
  `requestAnimationFrame` (не более одного обновления на кадр).

Профилирование на реальных 8 000 Pods ещё не выполнялось; эффект ниже —
ожидаемый, не измеренный.

Дата: 20.11.2026.

## 1. Короткий вывод

Виртуализация работает: в DOM находятся только видимые строки плюс overscan,
`TableRow` мемоизирован, layout-значения и callback'и уже стабилизированы. P1/P2
из общего performance-плана (watch вместо polling и переиспользование
`resourceVersion`) уже реализованы и помогают таблице.

Оставшиеся проблемы — это **работа O(n) на 8 000 строк, которая запускается
слишком часто**:

1. `allSelected` перебирает все 8 000 строк на каждом рендере `ResourceTable`,
   а `useVirtualizer` перерисовывает компонент при прокрутке.
2. `sorted` заново сортирует все 8 000 строк при каждом обновлении watch и при
   изменении любого Map из `cellContext`, даже если сортировка идёт по Name/Age
   и эти Map не используются.
3. `selectedObjects` и `selectedInView` в ResourceBrowser фильтруют 8 000 строк
   при каждом рендере, даже когда ничего не выбрано.
4. `filtered` всегда вызывает `resourceStatus` для каждой строки, даже когда
   поиск и фильтры выключены (ради `problemCount`).
5. Ресайз колонки вызывает `setPreviewWidths` на каждом `pointermove`, из-за
   чего перерисовывается вся таблица и все видимые строки.

Это статические выводы по коду. Профилирование на реальном кластере с 8 000
Pods ещё не выполнялось; конкретные миллисекунды ниже не заявляются.

## 2. Что уже оптимизировано (не ломать)

- `TableRow` — `memo`; callbacks передаются через стабильные `latest`-обёртки.
- `gridTemplate`, `stickyOffsets`, `minWidth`, `effectiveWidths` мемоизированы.
- Виртуализация с фиксированным `estimateSize`, без `measureElement` на каждой
  строке; высота строки задаётся `rowHeight`.
- `useResourceList` не делает полный list при живом watch (P1) и сохраняет
  object references при неизменном `resourceVersion` (P2).
- `sortedRef` сохраняет identity массива, если порядок не изменился.
- `useResourceMetrics`, `warnings`, `claimPods`, `serviceEndpoints`,
  `nodePodCounts` сохраняют identity Map при неизменном содержимом.
- Опции фильтров строятся лениво только при открытом popover.
- `WatchEventBatcher`, coalescing GET в kubeclient и strip `managedFields`
  работают и не относятся к таблице.

## 4. Props и identity

### Меняются без фактического изменения данных

- `cellContext` в ResourceBrowser: новый объект, если изменился любой из Map
  (`podMetrics`, `nodeMetrics`, `warnings`, `claimPods`, `serviceEndpoints`,
  `nodePodCounts`). Даже если активная сортировка — Name/Age, `sorted` memo
  пересчитывает все 8 000 строк.
- `previewWidths` при ресайзе: новый объект на каждый `pointermove`, из-за него
  меняются `effectiveWidths`, `gridTemplate`, `minWidth`; каждая видимая строка
  перерисовывается.
- `rows`: новый массив при каждом релевантном watch-батче. P2 сохраняет object
  references, но массив и `filtered` всё равно новые; `sorted` пересчитывается.
- `selectedKeys`: новый Set при каждом изменении выбора — ожидаемо, но
  производные массивы сейчас не мемоизированы.

### Стабильны

- `columns` (при неизменном порядке/видимости колонок).
- `stickyOffsets` и `gridTemplate` при неизменной ширине и pin-наборе.
- `podMetrics`, `nodeMetrics`, `warnings`, `claimPods`, `serviceEndpoints`,
  `nodePodCounts` при неизменном содержимом (A13).
- callbacks строк (`openRow`, `contextRow`, `menuRow`, `toggleRow`,
  `selectNamespace`, `openNode`, `openRef`).

## 5. Что заставляет перерисовывать видимые строки

- Любая Map из `cellContext` меняет identity → все видимые `TableRow`
  перерисовываются, хотя изменилась одна запись (метрики/ошибка/claim).
- Изменение `gridTemplate`/`stickyOffsets` при ресайзе или pin-колонке.
- `selected`, `checked`, `highlighted` — только затронутые строки; memo работает.
- `animateTop`/`shiftRows` — состояние таблицы меняет `top` transition; для
  больших списков transition уже отключён по `rows.length`, но state и таймер
  всё ещё срабатывают.
- `columns` меняется при скрытии/показе/перестановке колонок — ожидаемо.

## 6. Операции O(n) на 8 000

- `allSelected` — на каждый рендер/scroll.
- `selectedObjects`, `selectedInView` — на каждый рендер ResourceBrowser.
- `filtered` + `resourceStatus` — на каждое изменение `list.items`, даже без
  поиска и фильтров.
- `sortObjects` — на каждое изменение `filtered` или `cellContext`.
- `toggleAllSelection` — O(n) по клику (это нормально, не каждый рендер).
- `appendPage`/`reconcileItems` — O(n) на загрузку страницы (необходимо).
- `applyWatchEvents` — O(n) на батч watch (необходимо; уже один проход).

## 7. Подтверждено кодом vs требует профилирования

**Подтверждено кодом:**

- `allSelected` вызывается вне memo и перебирает `rows` на каждом рендере.
- `selectedObjects`/`selectedInView` не мемоизированы и не имеют early-return.
- `sorted` зависит от `cellContext`, поэтому метрики/события вызывают полную
  сортировку.
- `filtered` считает `resourceStatus` для всех строк даже при `narrowing=false`.
- ресайз колонки меняет state на каждое движение указателя.
- `shiftRows` state/timer работает независимо от того, отключена ли анимация
  для больших списков.

**Требует профилирования:**

- реальная цена `resourceStatus` на Pod/Node/Deployment при 8 000;
- цена `column.cell` для Pod/Node и влияние Map на количество re-render;
- какой overscan оптимален (16 может быть больше нужного, но менять без замеров
  не стоит);
- действительно ли `useVirtualizer` перерисовывает `ResourceTable` на каждом
  scroll-кадре (по API — да, но частоту нужно подтвердить Performance trace);
- влияние `transition-colors` и hover на compositor.

## 8. Предложения (9)

### R1. Мемоизировать `allSelected` и не считать его при пустом выборе

**Приоритет: высокий.**

**Проблема.** `ResourceTable.tsx` (около строки 339):
`rows.length > 0 && rows.every((row) => selectedKeys.has(...))` выполняется на
каждом рендере. `useVirtualizer` обновляет состояние при прокрутке, поэтому на
8 000 строках это 8 000 проверок на каждый scroll-тик, даже когда ничего не
выбрано.

**Решение.** Вычислять через `useMemo` по `[rows, selectedKeys]` с ранним
`selectedKeys.size === 0 → false`. Сохранить semantics «все видимые строки
выбраны»: `rows.every` остаётся, но только при непустом выборе. Если позже
понадобится избежать O(n) и при выборе, можно поддерживать счётчик выбранных
видимых строк, но это отдельный шаг.

**Ожидаемый CPU.** Убирает O(n)-скан на каждом scroll-кадре — наиболее частый
источник лишней работы.

**RAM/API/UX.** Без изменений.

**Сложность.** Низкая.

**Риски.** Низкие; не менять семантику Select All и выбранных строк вне фильтра.

---

### R2. Не пересортировывать 8 000 строк из-за Map, которые не участвуют в сортировке

**Приоритет: высокий.**

**Проблема.** `ResourceBrowser.tsx` (403–416) вызывает `sortObjects` каждый раз,
когда меняется `cellContext`. Метрики, warnings, claims и endpoints обновляются
периодически; даже сортировка по Name/Age заново строит decorated-массив и
сортирует все строки.

**Решение.** Передавать в зависимость `sorted` не весь `cellContext`, а
«sort-relevant context»: для активной колонки определить, использует ли она
метрики/события/claims/endpoints/pod counts. Для Name, Age, Status, Namespace и
других независимых колонок изменения этих Map не должны запускать сортировку.
`sortObjects` можно оставить прежним, но мемо не должно инвалидироваться
нерелевантным context. Это небольшой, локальный change; не нужно кешировать
объекты.

**Ожидаемый CPU.** На 8 000 строках убирает полную сортировку при каждом
обновлении метрик/warnings/claims (30–60 с), если открыта независимая колонка.

**RAM/API/UX.** Без изменений; сортировка остаётся точной для тех колонок, где
она зависит от Map.

**Сложность.** Низкая/средняя.

**Риски.** Не пропустить context-зависимую колонку (cpu/memory/warnings/pods/
endpoints); для неизвестной колонки лучше пересортировать, чем оставить старый
порядок.

---

### R3. Не делать полную сортировку при изменении одной строки watch-событием

**Приоритет: высокий/средний (сложнее R2).**

**Проблема.** `filtered` меняется при каждом watch-батче, `sorted` вызывает
`sortObjects` — O(n log n) на 8 000, хотя изменилась одна Pod. P2 сохраняет
object references, но не порядок: новый массив `filtered` всё равно запускает
полную сортировку.

**Решение (после R2).** Для сортировок, чей ключ не изменился (Name, Age,
Namespace, большинство status-колонок), определять изменённые объекты по
object reference/resourceVersion и либо сохранять прежний порядок, если значения
сортировки не изменились, либо переставлять только изменённые строки
(бинарная вставка/удаление). Для метрик, где сортировка зависит от Map, оставить
полную сортировку или инкрементально обновлять значения.

Не делать вторую систему кеширования объектов: использовать уже сохранённые
ссылки из `reconcileItems`.

**Ожидаемый CPU.** Убирает O(n log n) на частые watch-обновления; особенно важно
при 8 000 и активном churn.

**RAM.** Немного меньше временных decorated-массивов.

**API/UX.** Без изменений; порядок должен оставаться тем же, что даёт полная
сортировка.

**Сложность.** Средняя/высокая.

**Риски.** Ошибка в incremental-сортировке даёт неверный порядок. Нужен тест на
изменение sort value, добавление/удаление, tie-break и смену колонки. Если нет
уверенности — ограничиться R2 и измерением.

### R4. Мемоизировать производные выбора в ResourceBrowser

**Приоритет: высокий/средний.**

**Проблема.** `selectedObjects` и `selectedInView` (`ResourceBrowser.tsx`, 581 и
585) фильтруют 8 000 строк при каждом рендере, включая ввод в поиск и обновления
watch, даже когда `selectedKeys` пуст.

**Решение.** Ранний выход при `selectedKeys.size === 0` и `useMemo` по
`[list.items, sorted, selectedKeys]`. `selectedInView` нужен только для diff;
можно вычислять лениво только при `selectedKeys.size === 2`. Bulk-actions
продолжают использовать `selectedObjects`.

**Ожидаемый CPU.** Два O(n)-прохода на каждый рендер исчезают в обычном режиме;
при выборе пересчёт только при изменении выбора/строк.

**RAM/API/UX.** Без изменений; semantics выбора сохраняется.

**Сложность.** Низкая.

**Риски.** `selectedKeys` может содержать строки вне текущего фильтра — не
терять их в bulk-операциях; `selectedInView` должен оставаться в порядке
`sorted`.

---

### R5. Не вызывать `resourceStatus` для всех 8 000 строк, когда фильтры выключены

**Приоритет: средний/высокий.**

**Проблема.** В `filtered` (`ResourceBrowser.tsx`, 348–392) цикл всегда вычисляет
`resourceStatus(row, kind)` для подсчёта problems, даже если `searching`,
`problemsOnly` и column filters выключены. При каждом watch-батче это O(n)
дорогих status-вычислений, результат которых нужен только для счётчика проблем.

**Решение (минимальное).** Сначала измерить, сколько занимает `resourceStatus`
на 8 000 Pods. Если заметно — разделить:
- при `narrowing === false` не сканировать для фильтрации, но считать
  `problemCount` отдельно/лениво или на более редком основании;
- либо кешировать status по `WeakMap<KubeObject, ResourceStatus>`: P2 сохраняет
  ссылки, поэтому при watch-обновлении пересчитываются только новые объекты;
  память ограничена жизненным циклом уже существующих объектов.

Не отображать выдуманный/устаревший счётчик без согласования UX.

**Ожидаемый CPU.** Убирает повторный status-скан на неизменившихся объектах;
эффект зависит от цены `resourceStatus` (нужен профиль).

**RAM.** WeakMap на 8 000 небольших объектов; без роста сверх текущего списка.

**API/UX.** Без изменений; счётчик проблем должен остаться корректным.

**Сложность.** Низкая/средняя (зависит от выбранного варианта).

**Риски.** Кеш не должен переживать объект; `resourceStatus` зависит от kind,
поэтому ключ WeakMap должен учитывать kind или быть отдельным по kind.

### R6. Не перерисовывать таблицу на каждом `pointermove` при ресайзе колонки

**Приоритет: средний/высокий.**

**Проблема.** `ResourceTable.tsx` (487–510) на каждый `pointermove` вызывает
`setPreviewWidths({ ...current, [column.key]: finalWidth })`. Это меняет
`effectiveWidths`, `gridTemplate`, `minWidth`, перерисовывает заголовок и все
видимые строки; при 8 000 ресурсах это заметно даже при 60 видимых строках.

**Решение.** Минимальный шаг — throttle через `requestAnimationFrame`: не чаще
одного обновления на кадр. Лучше — держать preview в CSS-переменной на контейнере
(`--grid-template` / width колонки) и писать её в DOM напрямую при движении,
коммитить в store только на `pointerup`, как это уже делает sidebar drag. При
этом `gridTemplate` для строк должен читать CSS-переменную, а не React-prop.

**Ожидаемый CPU.** Снижает число рендеров таблицы при ресайзе до одного на кадр
или до одного на завершение; в idle — ноль.

**RAM/API/UX.** Без изменений; точность и коммит ширины сохраняются.

**Сложность.** Низкая (rAF) / средняя (CSS-переменная).

**Риски.** Не потерять `pointerup`/`pointercancel`, не сломать двойной клик
reset и sticky-колонки.

---

### R7. Не перерисовывать все видимые строки при изменении одной записи Map

**Приоритет: средний (требует профиля).**

**Проблема.** `TableRow` получает целые `podMetrics`, `nodeMetrics`, `warnings`,
`claimPods`, `serviceEndpoints`, `nodePodCounts`. Любое изменение Map даёт новую
identity → перерисовываются все видимые строки, хотя изменилась одна запись и
часто она не нужна этой строке.

**Решение.** Передавать в строку только вычисленные для неё значения (например,
`rowMetrics`, `rowWarning`, `rowClaimPods`), мемоизированные по object/Map
version; либо разбить ячейки на маленькие memo-компоненты с narrow props. Не
делать глубокое сравнение всех props — это будет дороже.

**Ожидаемый CPU.** Снижает re-render и повторный вызов `column.cell` при
метриках/warnings; в первую очередь для Pod/Node таблиц.

**RAM.** Небольшие per-row view-объекты; без второго кеша всех 8 000 объектов.

**API/UX.** Без изменений.

**Сложность.** Средняя.

**Риски.** Не размножить производные Map на 8 000; строить значения только для
видимых строк или по требованию. Нужно сохранить tooltip/status semantics.

---

### R8. Убрать `shiftRows` state/timer для больших списков

**Приоритет: средний.**

**Проблема.** В `ResourceTable.tsx` (277–292) эффект на каждое изменение длины
или первой строки делает `setShiftRows(true)` и ставит таймер на 200 мс. Для
8 000 строк анимация `top` уже отключена (`rows.length <= 1000`), но state и
таймер всё равно вызывают лишний рендер на каждый watch-батч.

**Решение.** При `rows.length > 1000` не включать `shiftRows` вовсе (обновить
`previousRows` и выйти). Лучше — сделать порог общей константой и не создавать
таймер для виртуализированных больших списков.

**Ожидаемый CPU.** Убирает лишний рендер и таймер при частых watch-обновлениях;
для малых таблиц анимация остаётся.

**RAM/API/UX.** Без изменений; большие списки и так без анимации.

**Сложность.** Низкая.

**Риски.** Не сломать анимацию при переходе через порог; при уменьшении списка
сбросить `shiftRows`.

---

### R9. Стабилизировать параметры виртуализатора (без изменения overscan)

**Приоритет: низкий; делать только после профиля.**

**Проблема.** `getScrollElement: () => scrollRef.current` и
`estimateSize: () => rowHeight` создаются заново каждый рендер. `useVirtualizer`
получает новый options-объект; при интенсивном scroll это лишние обновления
настроек. `overscan: 16` может быть избыточным, но уменьшать его без измерений
нельзя — возможны пустые полосы при быстром скролле.

**Решение.** Вынести `getScrollElement` в стабильный `useCallback`, а
`estimateSize` — в `useCallback([rowHeight])` или мемоизированный options-объект.
Overscan оставить 16 до Performance trace; измерить 8/12/16/24 и выбрать по
fps/пустым строкам, не по догадке.

**Ожидаемый CPU.** Небольшой; основной выигрыш — меньше churn настроек
виртуализатора, а не меньше DOM.

**RAM/API/UX.** Без изменений; не должно появиться пустых строк.

**Сложность.** Низкая.

**Риски.** Низкие; менять overscan только по замерам.

---

## 9. Что не делать

- Не отключать виртуализацию и не писать свою — текущая уже даёт только
  видимые строки.
- Не увеличивать overscan «на всякий случай».
- Не добавлять глобальный кеш 8 000 Kubernetes-объектов или второй вариант
  `Map`-кешей.
- Не делать `React.memo`/`useMemo` для каждой ячейки без профиля.
- Не выполнять глубокое сравнение `object`/Map на каждом рендере.
- Не переносить сортировку/фильтрацию в main.
- Не менять WatchEventBatcher, coalescing GET и P1/P2 identity.
- Не уменьшать частоту метрик/событий ради таблицы.
- Не менять внешний вид/поведение выбора и Select All.

## 10. Порядок внедрения и измерений

1. **R1** — самый безопасный и частый выигрыш (allSelected на scroll).
2. **R4** — убрать два O(n)-прохода из ResourceBrowser.
3. **R8** — убрать лишние state/timer для больших списков.
4. **R2** — не сортировать при нерелевантных Map.
5. **R6** — rAF-троттлинг ресайза; затем при необходимости CSS-переменная.
6. **R5** — только после профиля `resourceStatus`.
7. **R3** — incremental sort, только если R2/профиль покажут остаточную стоимость.
8. **R7** — per-row values, только если metrics/warnings реально дают массовые
   re-render.
9. **R9** — стабильные options; overscan только по trace.

Измерять на одном стенде:

- 8 000 Pods, таблица открыта, watch live;
- scroll 10 секунд, сортировка Name/Age/CPU, выделение одной строки, Select All;
- один watch-батч (1 / 50 / 250 изменений);
- обновление метрик и warnings;
- ресайз Name-колонки.

Метрики: CPU renderer, число рендеров `ResourceTable`/`TableRow` (React
Profiler), commit time, число вызовов `column.cell`, время сортировки,
количество DOM-строк (`role=row`), отзывчивость scroll, RAM.

Критерий: измеримое снижение CPU/рендеров без ухудшения scroll, точности
сортировки/выбора и без новых фоновых задач. Если эффект в пределах шума —
изменение не оставлять.
