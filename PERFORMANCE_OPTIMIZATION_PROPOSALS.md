# Performance optimisation proposals — mLens / FreeLens fork

Статус: **этап 1–3 (анализ, предложения, приоритизация)**; P1, P2 и K1 реализованы.

## 0. Статус реализации

- **P1 — реализовано.** Полный list при живом watch больше не выполняется; polling
  остаётся fallback для Helm и для watch в состоянии `off`/`connecting`/`error`.
- **P2 — реализовано.** Silent refresh сравнивает `uid + resourceVersion`,
  сохраняет прежний массив при отсутствии изменений и переиспользует object
  references для неизменившихся строк.
- **K1 — реализовано.** Одинаковые одновременные GET-запросы к одному
  `KubeConfig`/URL/timeout склеиваются на время выполнения в main. Это закрывает
  и P3 (list-level coalescing) — отдельная реализация P3 не нужна.
- Остальные предложения (P4–P8, K2, K3) пока не реализованы.

Измерения до/после на реальном большом кластере ещё не выполнены; ожидаемый эффект
описан ниже как оценка.

Изменений в коде приложения на этом этапе нет.

Дата: 20.11.2026.

## 1. Короткий вывод

Приложение уже содержит большое количество точечных оптимизаций: батчинг watch-событий
(150 мс / 250 событий), виртуализация таблицы, стабильные ссылки на Map/массивы
(`lib/stable.ts`), debounce поиска, ленивое построение фильтров, `limit=1` для sidebar
counts, strip `managedFields` на list-запросах, сохранение identity объекта деталей по
`resourceVersion`. Их не нужно переписывать.

Основные оставшиеся потери — не в «тяжёлых вычислениях», а в **повторной работе над
неизменившимися данными**:

1. Таблица продолжает раз в 30 секунд делать полный list, даже когда watch уже живой.
2. Каждый такой list заменяет массив объектов новыми копиями из IPC, из-за чего
   фильтрация, сортировка и memoized-строки пересчитываются без изменения данных.
3. Одинаковые list-запросы выполняются параллельно несколькими независимыми хуками
   (например, Pods для PVC-таблицы и PVC-деталей, Endpoints для Service-таблицы и деталей).
4. Скрытые workspace-ы открытых кластеров продолжают обрабатывать watch-события и
   обновлять React-состояние, хотя пользователь их не видит.
5. Вспомогательные данные (Node allocatable, Warning events) обновляются чаще, чем
   реально меняются, и заново строят Map даже при том же содержимом.

Ожидаемый эффект — прежде всего снижение CPU renderer/main на простое и при большом
числе объектов, уменьшение количества API-запросов и IPC-трафика. Точные цифры до
реализации не заявляются: они должны быть измерены на одинаковом стенде (см. §7).

## 2. Что уже работает и должно сохраниться

- `WatchEventBatcher` — один IPC-батч на ~150 мс, ERROR проходит сразу
  (`src/main/ipc/register.ts`).
- `ResourceWatcher` хранит `resourceVersion`, не пересылает BOOKMARK, переподключается
  и делает re-list только на 410/Expired (`src/main/kubernetes/resource-watcher.ts`).
- `useResourceList.applyWatchEvents` применяет весь батч за один проход и возвращает
  прежний массив при отсутствии релевантных событий.
- `useResourceMetrics`, `useWarningEvents`, `useServiceEndpoints`, `useClaimPods`,
  `useNodePodCounts` сохраняют identity Map при одинаковом содержимом (`lib/stable.ts`).
- Детали ресурса сохраняют identity объекта, если `resourceVersion` не изменился
  (`useResourceObject`, A18).
- Поиск debounce 200 мс; фильтры строятся лениво; таблица виртуализирована;
  `TableRow` мемоизирован.
- Counts в sidebar — `limit=1 + remainingItemCount` и только для открытой страницы,
  Nodes и CRD definitions.
- Скрытые кластеры уже не опрашивают counts/resources list (`refreshSeconds = 0`
  при `active = false`), но watches у них остаются (см. предложение 4).

## 3. Методика и ограничения анализа

- Анализ статический, по коду `src/main`, `src/renderer`, IPC-контракту.
- Профилирование в реальном большом кластере на этом этапе не выполнялось.
- Оценки CPU/RAM/API ниже — **ожидаемые**, а не измеренные. Их нельзя считать
  подтверждённым результатом до прогона §7.
- Приоритет ставится по отношению «польза / риск / сложность», а не по абсолютной

  достигаться ценой задержки при переключении кластеров или открытии ресурса.

## 4. Предложения (8)

### P1. Не делать полный list, пока watch жив

**Приоритет: высокий.**

**Проблема.** `useResourceList` запускает `setInterval(() => refresh(true), refreshSeconds * 1000)`
безусловно (`src/renderer/features/resource-browser/useResourceList.ts`, эффект около
строк 301–322). `refresh(true)` — это полный list (до 2000 объектов на scope) даже
когда `watchState === "live"`. При 30 секундах по умолчанию это ~120 полных списков в
час на каждую открытую таблицу, плюс повторная сериализация main → renderer.

**Причина нагрузки.**
- лишние Kubernetes API list-запросы;
- лишний IPC structured clone больших массивов;
- `setItems` новым массивом → новые объекты → повторная фильтрация/сортировка и
  повторный render видимых строк (memo по `object` не срабатывает, потому что пришли
  новые десериализованные объекты).

**Предлагаемое решение.** Включать fallback-poll только когда watch не живой:
`watchState !== "live"` (или `watchState === "off" | "error"`). Пока watch live,
таблица обновляется только событиями; ручной Refresh и событие
`mlens:resources-applied` продолжают работать. При переходе watch в error/off
интервал включается; при возврате в live — выключается. Для «тихого» пропуска
событий можно оставить очень редкий safety-list (например, раз в 5–10 минут), но
только если это подтвердится необходимостью.

**Ожидаемый CPU.** Снижение заметно на больших кластерах и при нескольких открытых
таблицах: минус полный list + десериализация + фильтрация/сортировка/рендер каждые
30 секунд на таблицу. В idle на маленьком кластере эффект небольшой, но лишняя работа
исчезает полностью.

**RAM.** Небольшое снижение пиков и мусора: меньше временных массивов и объектов,
создаваемых IPC-сериализацией. Долговременные кеши не добавляются.

**Kubernetes API.** Минус один list на scope на каждый интервал, пока watch жив.
Основной механизм обновления (watch) не меняется.

**UX.** Без ухудшения: live-обновления остаются; при падении watch появляется polling.
Риск: «живой, но молчащий» watch оставит таблицу устаревшей до reconnect/ручного
Refresh; fallback safety-list снижает этот риск.

**Сложность.** Низкая.

**Риски.** Нужно аккуратно добавить `watchState` в зависимости эффекта, чтобы смена
состояния не пересоздавала интервал на каждый батч; не отключать polling для Helm
(у него watch нет) и для случаев, когда watch недоступен.

### P2. Сохранять identity списка при silent refresh и обновлять только изменившиеся строки

**Приоритет: высокий.**

**Проблема.** В `fetchPage` (`useResourceList.ts`, около строк 185 и 215) результат
list всегда попадает в `setItems` как новый массив. Это происходит при ручном Refresh,
`mlens:resources-applied`, fallback-полинге и смене namespace. Даже если
`resourceVersion` всех объектов не изменился, renderer получает новые объекты и
считает данные изменившимися.

**Причина нагрузки.** Новый массив и новые object references обходят memoization
`TableRow`, заново запускают `filtered`/`sorted` memo, пересчитывают ячейки и
перерисовывают видимые строки. На 2–10 тыс. объектов это заметная работа на пустом
месте.

**Предлагаемое решение.**
1. Перед `setItems` сравнить дешёвую подпись: `uid + resourceVersion` в порядке
   прихода. Если подпись совпадает — оставить предыдущий массив.
2. Если изменилась только часть объектов — собрать новый массив, переиспользуя
   предыдущие object references для строк с тем же `uid` и `resourceVersion`.
   Это O(n) на уже полученном списке, без новых запросов и таймеров.
3. Для multi-namespace merge (`mergeByUid`) применять то же правило.

**Ожидаемый CPU.** Убирает полный render/filter/sort на no-op обновлениях. Особенно
важно для ручного Refresh и fallback-полинга. При живом watch и P1 почти не
задействуется, но защищает от повторных затрат.

**RAM.** Меньше краткоживущих копий объектов; старые ссылки переиспользуются.

**Kubernetes API.** Не меняет.

**UX.** Без изменений; таблица перестаёт «мигать» идентичными данными.

**Сложность.** Низкая/средняя.

**Риски.** `resourceVersion` — корректный признак изменения объекта, но нельзя
сравнивать только количество элементов. Нужно сохранять порядок и учитывать
добавленные/удалённые строки.

### P3. Склеивать одинаковые одновременные list-запросы в main

**Приоритет: высокий/средний.**

**Проблема.** Разные части UI независимо запрашивают одни и те же списки. Примеры:
- PVC-страница: `useClaimPods` таблицы и `useClaimPods` деталей (`StorageOverview`)
  оба листят Pods в namespace;
- Service-страница: таблица листит Endpoints (`useServiceEndpoints`), детали —
  Endpoints (`useServiceEndpointsDetail`) и EndpointSlices (`useServiceEndpointSlices`);
- при открытии деталей и таблицы одновременно совпадают list-запросы Pods/Events.

Каждый такой запрос — отдельный HTTP list и отдельный IPC-payload, хотя данные нужны
одни и те же в один момент времени.

**Причина нагрузки.** Дублирующие API-запросы и двойная сериализация больших списков;
на больших namespace это заметно и по CPU, и по времени ответа.

**Предлагаемое решение.** В main (на уровне `ClusterManager.list` или IPC-хендлера)
держать небольшой Map **in-flight** запросов по ключу
`clusterId|apiVersion|kind|namespace|selector|limit|continue`. Если такой запрос уже
выполняется — вернуть тот же Promise; удалить запись в `finally`. Это не TTL-кеш и
не фоновая задача: после завершения запроса данные больше не разделяются.
Не кешировать результаты между разными моментами времени.

**Ожидаемый CPU.** Минус дублирующие list + десериализация; особенно на PVC/Service
деталях и при первом открытии страницы. Небольшая дополнительная стоимость — Map
операций на запрос.

**RAM.** Кратковременно меньше одновременных массивов; кеш не растёт.

**Kubernetes API.** Убирает дубликаты именно в момент совпадения, не ухудшает
актуальность.

**UX.** Без изменений; ответы могут прийти чуть быстрее из-за меньшей конкуренции.

**Сложность.** Низкая.

**Риски.** Нельзя отдавать один и тот же mutable-массив разным потребителям, если
кто-то его мутирует; в текущем коде renderer массивы только читает. Запись должна
удаляться и при ошибке. Не делать из этого общий кеш «на 5 секунд» без измерений.

### P4. Не обновлять React-состояние таблиц скрытых кластеров от watch-событий

**Приоритет: средний (растёт с числом открытых кластеров).**

**Проблема.** `AppShell` держит смонтированными workspace всех посещённых кластеров и
скрывает неактивные CSS-классом (`sessionIds.map`, `hidden`). `useResourceList` не
получает `active`; его watch-подписки продолжают работать, батчи применяются к
`items`, React-дерево скрытой таблицы перерисовывается. Polling у скрытых уже
выключен, но watch-события — нет.

**Причина нагрузки.** На нескольких кластерах с активными изменениями (rollout,
autoscaling, churn Pods) скрытые таблицы потребляют CPU на `applyWatchEvents`,
фильтрацию/сортировку и React render, хотя пользователь их не видит. Нагрузка растёт
линейно от числа открытых кластеров и скорости изменений.

**Предлагаемое решение (минимальный риск).** Передавать `active` в `useResourceList`:
- пока workspace скрыт — не применять батчи к React-состоянию; обновлять только
  `resourceVersion` в ref и помечать таблицу «stale»;
- при активации — один silent refresh (текущие строки остаются на экране) и
  продолжение watch с последнего RV.
  
Альтернатива: останавливать подписки скрытого workspace и переподписываться при
активации; это проще по CPU, но добавляет list при переключении. Выбор — после
измерения задержки переключения; предпочтителен вариант с отложенным применением.

**Ожидаемый CPU.** Существенное снижение при 2+ открытых кластерах с активными
изменениями; на одном кластере эффекта нет.

**RAM.** Меньше обновлений/мусора; очередь событий не хранится (только RV).

**Kubernetes API.** Возможен один дополнительный refresh на активацию скрытого
workspace; watches можно сохранить. Итог зависит от сценария, измерять.

**UX.** Таблица при возврате к кластеру может на мгновение показать старые строки до
silent refresh; спиннер не показывать. Переключение не должно замедляться.

**Сложность.** Средняя.

**Риски.** Нельзя терять события без последующего refresh; нужно чётко закрывать
очередь при dispose. Не сломать текущий принцип «один mounted workspace на кластер».

### P5. Переиспользовать side-data таблицы в деталях вместо второго независимого fetch

**Приоритет: средний.**

**Проблема.** `ResourceBrowser` уже строит `claimPods`, `serviceEndpoints`,
`warningEvents` и передаёт их в `CellContext` (`ResourceBrowser.tsx`, около строк
234–300). Детали тех же ресурсов снова запрашивают те же данные:
- `StorageOverview` вызывает `useClaimPods` для PVC;
- `ServiceOverview` вызывает `useServiceEndpointsDetail` (Endpoints) и
  `useServiceEndpointSlices`.

При открытых деталях это дублирует list Pods/Endpoints/EndpointSlices.

**Причина нагрузки.** Дублирующие запросы (см. P3), повторное построение Map,
лишние обновления состояния деталей.

**Предлагаемое решение.** Пробел в данных — отсутствие общего канала между таблицей и
редактором. Ввести небольшой React context на уровне `ClusterWorkspace` (или
`ResourceBrowser` + `EditorArea`), который отдаёт уже вычисленные side-maps и
`serviceEndpointSlices`. Детали используют данные, если они есть для нужного
kind/namespace/claim, иначе делают собственный fetch (fallback для Related/поиска).
Никаких глобальных кешей и таймеров.

**Ожидаемый CPU.** На PVC/Service-деталях — меньше list/Map-построений и меньше
рендеров от повторных ответов.

**RAM.** Меньше одновременных копий списков.

**Kubernetes API.** Минус дублирующие Pods/Endpoints-запросы при открытых деталях.

**UX.** Без изменений; данные те же и обновляются тем же poll таблицы.

**Сложность.** Средняя.

**Риски.** Контекст не должен ререндерить workspace на каждый poll; передавать только
стабильные Map. Детали могут быть открыты без соответствующей таблицы — fallback
обязателен.

### P6. Обновлять Node allocatable реже, чем Pod/Node metrics

**Приоритет: средний.**

**Проблема.** `useResourceMetrics` при открытой таблице Pods каждые ~60 секунд
запрашивает PodMetrics, NodeMetrics **и все Nodes** только ради allocatable в
tooltip (`useResourceMetrics.ts`, около строк 165–200). Nodes меняются намного реже,
чем метрики.

**Причина нагрузки.** Лишний list всех Nodes и парсинг `status.allocatable` каждую
минуту; на 1000 нод это заметно, хотя цифры почти не меняются.

**Предлагаемое решение.** Разделить жизненный цикл:
- PodMetrics/NodeMetrics — текущий интервал (≥60 с);
- Node allocatable — отдельный редкий интервал (например, 5 минут) или обновление
  только при смене набора Node/их `resourceVersion`; можно переиспользовать уже
  загруженные Node-объекты, если они есть в сессии.

**Ожидаемый CPU.** Минус ~4/5 запросов Nodes и парсинга allocatable при открытой
таблице Pods; на маленьких кластерах эффект мал, но лишняя работа исчезает.

**RAM.** Практически без изменений; меньше временных массивов Node.

**Kubernetes API.** Заметно меньше list Nodes; Pod/Node metrics не меняются.

**UX.** Capacity/allocatable в tooltip может отставать до 5 минут — это приемлемо для
редко меняющегося значения. CPU/Memory usage остаются минутными.

**Сложность.** Низкая.

**Риски.** Если ноды часто добавляются/меняются, tooltip временно покажет старую
ёмкость; не влиять на сортировку по usage.

### P7. Обновлять детали открытого ресурса от watch, а не только по таймеру 15 секунд

**Приоритет: средний/низкий.**

**Проблема.** `useResourceObject` опрашивает `api.resources.get` каждые
`min(15, refreshSeconds)` секунд (`ResourceDetails.tsx` около строки 143,
`useDetailsData.ts` 63–75). При 4 pane-ах это до 16 GET/минуту, даже если объект не
менялся.

**Причина нагрузки.** Лишние GET и обновления деталей. `resourceVersion` identity
защищает React от лишнего рендера, но сеть/десериализация уже потрачены.

**Предлагаемое решение.** Если открытый ресурс присутствует в watch-списке текущей
таблицы, обновлять детали по `uid/resourceVersion` из этого списка; оставить
редкий fallback (например, 60 с) для деталей, открытых из Related/поиска, и для
kind, который не совпадает с текущей таблицей. Не добавлять новых подписок: детали
могут использовать уже существующий поток данных таблицы через тот же контекст, что
в P5.

**Ожидаемый CPU.** Меньше GET/десериализации/рендеров при открытых деталях; при
активных изменениях детали обновятся даже быстрее, чем раз в 15 секунд.

**RAM.** Без роста.

**Kubernetes API.** Минус GET на неизменившийся объект; watch уже есть.

**UX.** Детали остаются live; fallback сохраняет работу для ресурсов вне таблицы.

**Сложность.** Средняя.

**Риски.** Связь деталей с таблицей может усложнить открытие из Related/Command
Palette; нужен явный fallback и отсутствие циклических зависимостей.

### P8. Снизить стоимость Warning events: signature-check и более редкий poll

**Приоритет: низкий/средний.**

**Проблема.** `useWarningEvents` при таблице Pods/Deployments/... каждые
`max(30, refreshSeconds)` секунд листит все Warning Events (`limit=1000` на
namespace), затем заново строит Map (`useWarningEvents.ts`, 34–123). Даже если
события не изменились, массив `events` новый, Map строится заново и сравнивается.

**Причина нагрузки.** На кластере с большим числом событий — дорогой list + IPC +
O(n) построение/сравнение Map каждые 30 секунд. Полезность обновления редко требует
такой частоты.

**Предлагаемое решение (минимальный вариант).**
1. Перед `setEvents` сравнивать подпись `uid + resourceVersion` (или
   `count + lastTimestamp`) и сохранять прежний массив, если предупреждения не
   изменились; тогда Map не пересобирается.
2. Увеличить минимальный интервал warning-полинга до 60–120 секунд (или сделать его
   отдельной настройкой, если нужна свежесть). Watch Events — возможная альтернатива,
   но это новая подписка и больше сложности; начинать с пункта 1 и интервала.

**Ожидаемый CPU.** Снижение на кластерах с большим числом Events; на маленьких —
незначительное.

**RAM.** Меньше временных массивов/Map.

**Kubernetes API.** Минус часть list Events.

**UX.** Warning-бейдж может обновляться на минуту позже. Это приемлемо для
вспомогательной колонки; при активных проблемах Events обычно живут дольше.

**Сложность.** Низкая.

**Риски.** Если увеличить интервал слишком сильно, оператор позже увидит новое
предупреждение. Не менять интервал без согласования UX.

## 5. Приоритизация

### Высокий приоритет (делать первыми, изолированно, с измерениями)

1. **P1** — не поллить list при живом watch.
2. **P2** — сохранять identity списка и переиспользовать неизменившиеся строки.
3. **P3** — склеивать одинаковые in-flight list-запросы.

### Средний приоритет

4. **P4** — не обновлять скрытые таблицы от watch-событий; refresh при активации.
5. **P5** — переиспользовать side-data таблицы в деталях (claim pods, endpoints).
6. **P6** — реже обновлять Node allocatable.
7. **P7** — детали от watch с редким fallback.

### Низкий приоритет

8. **P8** — signature-check и более редкий warning poll; только после P1–P3.

## 6. Что не стоит делать

- **Не добавлять глобальный informer/кеш всех ресурсов.** Память, CPU на парсинг и
  сложность инвалидации превысят пользу для десктопного приложения.
- **Не переносить фильтрацию/сортировку в main.** Это усложнит IPC и не даст
  выигрыша при уже виртуализированной таблице.
- **Не добавлять `React.memo`/`useMemo` повсеместно.** Уже есть мемоизация строк и
  стабильные Map; бессмысленные обёртки добавят стоимость сравнения.
- **Не уменьшать глобальный `refreshIntervalSeconds`.** Это ухудшит API-нагрузку и
  ничего не даст при живом watch.
- **Не заменять watch на polling и наоборот** без доказанной проблемы.
- **Не вводить TTL-кеш списков «на 5 секунд».** P3 ограничивается in-flight
  запросами; TTL создаст риск устаревших данных и потребует инвалидации.
- **Не кешировать бесконечно** большие списки Pods/Events/Endpoints.
- **Не трогать существующий `WatchEventBatcher` и debounce поиска** без профиля:
  они уже решают основные burst-сценарии.

## 7. План измерений (обязателен до/после каждой оптимизации)

Одинаковый стенд и сценарий:

1. 1 кластер, ~5–10 тыс. Pods, 1–2 тыс. Deployments, 200 Namespaces, 100 Nodes.
2. 2 кластера, у каждого открыта таблица Pods; один кластер скрыт.
3. Idle 5 минут без действий.
4. Активная работа: смена kind, фильтр, поиск, сортировка, открытие деталей, split.
5. Burst: rollout/scale, создающий 50–200 watch-событий.

Метрики:

- CPU main и renderer отдельно (Activity Monitor / `process.getCPUUsage()` на время
  профиля);
- RSS main + renderer + GPU;
- количество list/get/watch-запросов за 60 секунд (временный счётчик в main, не
  коммитить в релиз);
- количество IPC-батчей/сообщений (временный счётчик);
- число рендеров ключевых компонентов (React Profiler) и время commit;
- задержка переключения кластера/открытия ресурса (ручной замер или Performance
  trace);
- отсутствие роста памяти за 30–60 минут.

Критерий принятия: измеримое снижение CPU/API без ухудшения времени открытия,
переключения и отзывчивости; отсутствие роста RAM и ошибок. Если эффект в пределах
шума — изменение не оставлять.

## 7.1. Дополнительные предложения по kubeclient (main process)

Ниже — то, что можно сделать именно в слое `@kubernetes/client-node` / `kubeRequest` /
discovery, не дублируя renderer-оптимизации.

### K1. In-flight coalescing одинаковых GET-запросов в `kubeRequest`

**Приоритет: высокий. Предпочтительная форма P3 — реализовать один раз здесь.**

**Проблема.** `kubeRequest` (`src/main/kubernetes/http.ts`) выполняет каждый вызов
отдельно: новый `RequestContext`, auth, HTTP request, буферизация и `JSON.parse`.
Одинаковые GET-запросы приходят из независимых хуков (Pods для PVC-таблицы и деталей,
Endpoints для Service-таблицы и деталей), из discovery, counts и `get` открытых
деталей. P3 решает только list через `ClusterManager`; на уровне kubeclient можно
покрыть весь GET-трафик.

**Решение.** Для `method === "GET"` держать `WeakMap<KubeConfig, Map<key, Promise>>`,
где key — канонический URL с query (метод/URL; `timeoutMs` учитывать в ключе или
использовать разумный общий). Если такой запрос уже в полёте — вернуть тот же Promise;
удалять запись в `finally`. Это **не TTL-кеш**: после завершения запроса данные не
разделяются, устаревание невозможно. Не коалесить `POST/PUT/PATCH/DELETE`, watch,
logs, exec и port-forward (они не идут через `kubeRequest`).

**Ожидаемый CPU.** Меньше HTTP-сессий, `JSON.parse` и IPC-payload в моменты, когда
разные части UI просят одно и то же. Основной выигрыш — на PVC/Service-деталях,
`counts` и discovery.

**RAM.** Меньше одновременных копий больших массивов; сам Map крошечный и очищается
сразу.

**Kubernetes API.** Минус дублирующие GET; актуальность не страдает.

**UX.** Без изменений; при совпавших запросах ответ может прийти быстрее.

**Сложность.** Низкая/средняя.

**Риски.** Все потребители должны считать ответ read-only. `stripServerMetadata`
мутирует объект, но повторное удаление того же поля идемпотентно; лучше вынести
strip в место, где объект создаётся один раз. Ошибка одного общего запроса
отклоняет все присоединившиеся Promise — это ожидаемо. Учитывать, что KubeConfig
с ротацией токена — один объект; in-flight живёт секунды, риск устаревшего токена
минимален.

---

### K2. Ограничить частоту форсированного discovery при неизвестном kind

**Приоритет: средний.**

**Проблема.** `ResourceCatalog.get` (`src/main/kubernetes/session.ts`) при отсутствии
kind делает `refresh(true)`: полный discovery — `/api/v1`, `/apis`, список CRD и
запросы по всем API-группам с ограничением concurrency 6. Если kind устарел,
опечатан или UI повторяет один и тот же отсутствующий вид (Related, fallback
деталей, watcher), каждый такой вызов заново запускает дорогой discovery. In-flight
dedup в `DiscoveryService` помогает только на время одного скана, не между
последовательными попытками.

**Решение.** В `ResourceCatalog.get` запоминать время последнего forced-refresh и
повторять полный discovery не чаще, например, одного раза в 30 секунд. Ввести
короткий negative-cache на `apiVersion|kind` (10–30 с), чтобы серия одинаковых
промахов не возвращалась к сети. При явном обновлении discovery/установке CRD —
сбрасывать negative-cache.

**Ожидаемый CPU.** Убирает «шторм» полного discovery в редких, но дорогих сценариях;
на нормальном пути эффекта нет.

**RAM.** Минус временные массивы discovery; negative-cache — несколько строк.

**Kubernetes API.** Резко меньше запросов при ошибке/опечатке; discovery не меняется.

**UX.** Установленный только что CRD может появиться на несколько секунд позже, если
перед этим был промах. Приемлемо; нужен способ явно обновить каталог.

**Сложность.** Низкая.

**Риски.** Не закешировать навсегда реально новый вид; TTL должен быть коротким.
Не менять поведение успешного discovery.

---

### K3. Отменять устаревшие list-запросы, а не только игнорировать их результат

**Приоритет: средний/низкий (зависит от сценариев переключения).**

**Проблема.** Renderer защищается generation-счётчиком (`useResourceList`): старый
ответ не попадает в state, но main уже скачал его, распарсил JSON и отправил через
IPC. При быстром переключении kind/namespace, `loadAll` на 20 страниц или уходе со
страницы старые list-запросы продолжают выполняться и потреблять CPU/сеть. Особенно
заметно на больших списках с continue token.

**Решение.** Добавить в контракт list-запроса необязательный `requestId`/abort и в
main отменять предыдущий HTTP-запрос для того же табличного scope
(`clusterId + apiVersion + kind + namespace`). Не отменять запрос, если на него
подписан другой потребитель (учитывать ref-count от K1). Как более простой первый
шаг — останавливать сам цикл `loadAll`, когда поиск/фильтр уже сброшен, не запрашивая
следующие страницы.

**Ожидаемый CPU.** Меньше парсинга/сериализации в моменты навигации; в idle ноль.

**RAM.** Меньше одновременно живущих больших JSON-массивов.

**Kubernetes API.** Отмена освобождает соединение; новых запросов не добавляет.

**UX.** Переключение должно стать отзывчивее; текущие строки не мигают.

**Сложность.** Средняя: меняется IPC-контракт, нужна аккуратная работа с K1 (общий
Promise нельзя отменять, пока им пользуется другой потребитель).

**Риски.** Не отменить запрос, который нужен другому компоненту; не сломать
`continue`-пагинацию; отмена не должна выглядеть как ошибка в UI.

---

### Что в kubeclient делать не стоит

- **Кешировать auth-заголовки/`RequestContext` дольше, чем это уже делает
  client-node.** Риск устаревшего токена/exec-plugin (EKS/GKE/AKS) выше выгоды;
  сначала нужно доказать профилем, что `applySecurityAuthentication` — горячая точка.
- **Добавлять gzip/ручной streaming JSON-парсер ради list-ответов.** Экономия сети
  может обернуться дополнительным CPU на декомпрессию/парсинг; приоритет проекта —
  CPU, а не трафик.
- **Делать TTL-кеш list/get в main.** P3/K1 ограничены in-flight; TTL потребует
  инвалидации по resourceVersion/watch и легко даст устаревшие данные.
- **Увеличивать `timeoutSeconds` watch без необходимости.** Реконнект раз в 300 с
  дешёвый; длинный таймаут увеличивает окно молчаливой потери событий.
- **Кешировать discovery на диск.** Старт станет быстрее, но появится риск устаревшей
  схемы и лишняя логика инвалидации; текущий TTL 5 минут достаточен.

## 11. Runtime profile — 20.11.2026

### Что и как измерялось

Собранное приложение `v2.4.89`, macOS arm64, окно открыто на странице каталога,
кластер не подключён. Метрики получены через Chrome DevTools Protocol:

- `window.mlens.app.metrics()` — суммарные CPU/RAM по процессам Electron;
- `performance.memory.usedJSHeapSize` — JS heap renderer;
- `document.querySelectorAll("*").length` — размер DOM;
- `ps`/`top` — RSS и CPU отдельных процессов (main, renderer, GPU, network).

Профиль снимался дважды: сразу после старта и через 30 секунд простоя.

### Результаты (каталог, без подключённого кластера)

| Показатель | t≈0 | t≈30 s |
|---|---:|---:|
| CPU всех процессов Electron | 1.4% | 0.0–0.3% |
| RAM всех процессов (`app.getAppMetrics`) | 421 MB | 286 MB |
| JS heap renderer | 23.1 MB | 23.1 MB |
| DOM-узлов | 2914 | 2914 |

Отдельные процессы после прогрева:

- main — ~115 MB RSS;
- renderer — ~127 MB RSS (кратковременно до ~208 MB на старте);
- GPU — 74–278 MB RSS, сильно колеблется;
- network utility — ~7 MB.

### Выводы

1. **JS-память приложения на каталоге не течёт**: heap 23.1 MB не изменился за
   30 секунд, DOM стабилен. 421 → 286 MB — это в основном стартовые буферы
   Chromium/GPU, которые отдаются обратно.
2. **Idle CPU оптимизировать нечего**: после прогрева 0–0.3% суммарно.
   Добавлять throttling/фоновые задачи не нужно.
3. **Большая часть RSS — Chromium/GPU, а не React-состояние.** GPU-процесс может
   занимать больше renderer-а; это обычное поведение Electron и не лечится
   отключением аппаратного ускорения без роста CPU.
4. **Профиль таблицы 8 000 Pods получить не удалось**: локальный kubeconfig
   `localhost:55000` недоступен, а подключаться к prod/preprod кластерам без
   явного разрешения нельзя. Поэтому цифры для таблицы ниже не измерены.
5. При открытом каталоге из ~100 контекстов каталог строит ~2.9k DOM-узлов —
   умеренно; оптимизировать карточки каталога смысла нет.

### Что проверять на реальном тестовом кластере

Для кластера с 8 000 Pods нужен отдельный прогон:

1. открыть таблицу Pods, дать watch стабилизироваться;
2. 30 секунд idle;
3. scroll 10 секунд;
4. сортировка Name / CPU / Memory;
5. выделение одной строки и Select All;
6. один watch-батч и серия из 200 изменений;
7. ресайз Name-колонки;
8. открытие деталей Pod.

Снимать `app.getAppMetrics()`, `performance.memory`, число DOM-узлов
(`document.querySelectorAll('[role=row]').length`) и React Profiler. Только после
этого можно подтвердить эффект R1–R6 и P1–P2 в миллисекундах/мегабайтах.

### Кандидаты на RAM-оптимизацию (после профиля)

- **Неактивные workspace-ы**: они остаются смонтированными и держат
  `resource`-массивы, состояния таблиц и editor tabs. Если профиль покажет рост
  RAM от числа открытых кластеров, обсудить освобождение только тяжёлых
  resource-массивов (не UI-состояния) для кластеров, скрытых дольше N минут.
- **Крупные открытые вкладки деталей**: каждая держит свой KubeObject/YAML; при
  десятках вкладок это заметно. Не ограничивать без измерения; возможен мягкий
  лимит или очистка YAML-буфера неактивной вкладки.
- **Логи**: буфер ограничен 20 000 строк, но строки могут быть длинными;
  проверять отдельно на chatty-контейнере.

Пока эти пункты не реализуются: на каталоге доказанной проблемы с JS-памятью
нет, а без профиля 8 000 ресурсов любое усложнение будет преждевременным.

- Дополнительные кеши resource-объектов не нужны: P2 уже переиспользует
